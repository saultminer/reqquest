# ReqQuest

ReqQuest is a **platform** (not a finished app) for building benefit-application systems: an organization offers one or more programs, applicants prove eligibility, reviewers approve or deny. Downstream projects install `@reqquest/api` and `@reqquest/ui`, then define their own programs, requirements, and prompts in code. The full domain model is described in [README.md](README.md); read it when working on domain logic.

## Repo layout

- [api/](api/) — `@reqquest/api`, the GraphQL API library (fastify + type-graphql via `@txstate-mws/graphql-server`, MySQL via `mysql2-async`). Domain folders under `api/src/` (appRequest, application, requirement, prompt, program, period, access...). `api/src/registry/` holds the definition interfaces downstream projects implement.
- [ui/](ui/) — `@reqquest/ui`, the SvelteKit UI library (`@txstate-mws/carbon-svelte`). `ui/src/local/` contains the demo projects' prompt components. [ui/src/lib/components.md](ui/src/lib/components.md) is the UI-authoring reference — the prompt-component contract, registration recipes, and the full component catalog with props. It is generated from [ui/docs-src/components/](ui/docs-src/components/) plus the design system's published `llms/*.md` docs, filtered to what the installed carbon-svelte actually exports; run `npm run docs:components` in [ui/](ui/) after bumping that dependency. It lives in `src/lib` on purpose: `svelte-package` copies non-code files there into `dist` verbatim, so `"files": ["dist"]` ships it to downstream projects at `node_modules/@reqquest/ui/dist/components.md` — the one piece of our UI documentation that reaches them, since `ui/CLAUDE.md` and `docs/` do not.
- **The app shell ships in `@reqquest/ui` and downstream projects build it, not just import from it.** `npm pack` runs [ui/scripts/pack-app.js](ui/scripts/pack-app.js), which copies `src/routes`, `src/internal`, `app.html`, `static` and the nginx runtime into `ui/app/` (gitignored, not in `exports`). The `reqquest-ui` bin ([ui/bin/reqquest-ui.js](ui/bin/reqquest-ui.js), [ui/cli/](ui/cli/)) assembles a downstream `.reqquest/` SvelteKit project from it, overlays the project's own `src/routes` (override per file, `.reqquest-replace` per folder, `disableRoutes`, drift-locked in `reqquest-overrides.lock.json`), and builds with config from [ui/cli/config.js](ui/cli/config.js) - so downstream declares only `@reqquest/ui`. svelte, kit, vite and vite-plugin-svelte are exact-pinned **peers** (they must be single top-level copies; as plain deps npm nested ours under kit's newer auto-installed peers), and `sync` refuses a mismatched install because npm only *warns* on one. Consequences for work here: **the shell must stay relocatable** - in `src/routes` and `src/internal` import the library as `@reqquest/ui` (not `$lib`; a second copy of the registry/stores would load downstream) and the registry as `$local` (not `../local`); `pack-app.js` fails the pack on a relative import leaving the shell. [ui/cli/config.js](ui/cli/config.js) mirrors `ui/svelte.config.js` + `ui/vite.config.ts`; change them together. Bumping a toolchain package means bumping its pin in `ui/package.json`. `ui/scripts/test-overlay.sh` (node 22+) packs and builds `ui/test-fixture/` end to end. Downstream guide: [docs/downstream-ui.md](docs/downstream-ui.md).
- [demos/](demos/) — runnable demo instances (pet-adoption theme): `simple`, `default`, `multi`, `complex`, `rc`. Each shows the downstream-developer pattern: a `RQServer` started with definitions for programs, requirements, and prompts.
- [test/](test/) — Playwright e2e tests. Run with root `./test.sh`. `up.sh` to run one of the demos (CLI args to choose a demo).
- [docs/](docs/) — sitemap and user stories.

**Regenerate demo keys after changing a definition** — `npm run keys:generate` in [demos/](demos/). `demos/src/keys.generated.d.ts` is generated from the definitions and is what makes `promptKeys`, `requirementKeys` and friends autocomplete and reject typos. It goes stale when a definition is added, removed, renamed, or re-keyed; `./test.sh` runs `keys:check` up front and refuses to proceed on a stale file. It also emits `ui/src/local/keys.generated.d.ts`, which types the UI's component registration. Hot reload regenerates both: the dev stack bind-mounts that one file into the api container and nodemon runs `keys:generate:dev`, so a prompt added on the API side is a valid UI key as soon as you save. That relative `../ui/src/local` path is a monorepo shape and does not transfer — a downstream project whose API definitions and UI live in separate repos has no shared watcher and must regenerate in CI or on dependency install. `./test.sh` checks both files either way — in docker, via the `keycheck` stage of `demos/Dockerfile`, so it needs nothing built locally (CI runs it before any image exists). Generating still needs `api/dist`. Note the dev stack deletes and rebuilds it on every change to `api/src` or `demos/src`, so run these when the stack is idle — mid-rebuild you get a confusing "could not resolve '@reqquest/api'" or a module-not-found instead.

**Keeping the UI's component registry in step with the API.** The key declaration only rejects *unknown* keys; on its own it cannot require the keys the API *does* have. Coverage comes from `UIConfig`'s keyed form (`prompts: { some_prompt: { formComponent, displayComponent } }`) — a `Record` over the key union, so a prompt added on the API side and never registered is a build error. Only `prompts` requires full coverage; `requirements` and `programs` are partial, because those definitions carry nothing but optional decoration (an icon, a configure component) and every consumer optional-chains them. The array form still works and is still unchecked. Because the generated union spans every demo in this repo, each demo's config is checked against a per-demo alias (`SimplePromptKey`, `RcPromptKey`, …) emitted by the analyzer's `--groups` flag — see `keys:generate:ui` in [demos/package.json](demos/package.json). `multi` has no definitions of its own; it imports `default`'s, so it is typed against `Default*Key`.

Two layers enforce coverage, both at build time:
- **Build:** `npm run check:registry` in [ui/](ui/) ([ui/check-registry.js](ui/check-registry.js)), run by [ui/Dockerfile](ui/Dockerfile). Narrowed to `src/local/index.ts` deliberately — the full `npm run check` still reports ~58 pre-existing errors elsewhere, so it cannot be the gate yet. Widen it once those are cleared.
- **CI:** `demos/Dockerfile`'s `build` stage runs `FROM keycheck`, so `keys:check` is in the path of every image build rather than only `./test.sh`.

At runtime the behaviour is **degradation, not detection**: `UIRegistry.warnIfMissing` logs an ungated `console.error` naming the key, and `MissingDefinitionNotification` renders in place of the component, so a missing prompt never white-screens. There is deliberately no boot-time reconciliation against the API — it was built and removed. It required exposing `Query.prompts`/`Query.requirements`, which have **no authorization** and would hand the full definition catalog to any authenticated user; that is a bad trade for a diagnostic when downstream apps keep their UI and API in one repo and the build gate already catches drift before merge.

Two gaps follow from that and are known, not overlooked. The first - the registry gate not reaching downstream projects - is closed: downstream UIs build with `npx reqquest-ui build`, which runs the same narrowed check (`reqquest-ui check-registry`, a port of `check-registry.js`) before `vite build`, so they get it without wiring anything. Verified against a packed tarball in a project with no `paths` mapping: the `declare module '@reqquest/ui'` augmentation merges correctly through `dist/index.d.ts`'s re-export, a missing prompt is a named error, an unaugmented project degrades to `string`, and the array form still compiles while still rejecting typos. The second gap is a browser-cached SPA bundle running against a newer API; the API has dormant `schemaVersion` guards for exactly that ([api/src/prompt/prompt.resolver.ts](api/src/prompt/prompt.resolver.ts), *"Client is out of date. Please refresh."*) which the UI never actually sends.

**The key generator is an API-repo tool.** `findManyDefinitionExports` builds a real `ts.createProgram` over the definitions' `.ts` **sources**, so a downstream UI repo that only consumes a published `@reqquest/api` cannot generate its own declaration — it can only receive one (that is what `--module '@reqquest/ui'` is for) or run `--check-keys` if it has the API sources on disk. That handoff has no automated enforcement across a repo boundary, which is exactly why the runtime layer above exists.

**Run `npm install` in [demos/](demos/) before relying on your editor there.** It is the one package that is not needed for the docker workflow, so it is easy to leave uninstalled — and when it is, `@reqquest/api` and five other modules do not resolve, every type in `demos/src` becomes an error type, and nothing is checked. Typed key references (`promptKeys`, `requirementKeys`) then silently accept typos in the editor while still failing in the container. `@reqquest/api` resolves to `api/dist`, which is bind-mounted and rebuilt by the running stack, so restart the stack after changing `api/src` to refresh the types the editor sees.

## Domain model (condensed)

- **Period** — an application window with open/close/archive dates. Configurations/enabling/disabling (of prompts/requirements/programs) are per-period and lock as reviews begin.
- **AppRequest** — one applicant's entire submission within a period. Contains one **Application** per program.
- **Program** — a benefit. Each program has an ordered list of requirements.
- **Requirement** — a procedural business rule ("applicant must provide proof of X", paired with "reviewer must evaluate proof of X"). Has a type binding it to a phase: PREQUAL, QUALIFICATION, POSTQUAL, PREAPPROVAL, APPROVAL, ACCEPTANCE, WORKFLOW. Its developer-written logic evaluates collected prompt data and returns an **ApplicationRequirement** status: PENDING, MET, DISQUALIFYING, WARNING (passing-with-caveat), NOT_APPLICABLE. Logic must return PENDING until no further answer could change the result; once non-pending the status must be stable.
- **Prompt / PromptAnswer** — a data-collection screen (a Svelte component) and the answered data per app-request. Requirements consume prompt data only after the prompt is fully "answered" (developer-defined). Prompts are revealed one at a time per requirement while it stays PENDING, so only needed data is collected. Prompts can be shared across requirements; `promptKeysAnyOrder` and `promptKeysNoDisplay` are special dependency modes.
- **Lifecycle** — AppRequest phases: PREQUAL → QUALIFICATION → POSTQUAL → READY_TO_SUBMIT → (submit) → PREAPPROVAL → APPROVAL → blocking WORKFLOW stages → REVIEW_COMPLETE → optional ACCEPTANCE → APPROVED/NOT_APPROVED or ACCEPTED/REJECTED → non-blocking WORKFLOW → COMPLETE. Applications also carry a status (PENDING/ELIGIBLE/INELIGIBLE/ACCEPTED/REJECTED) independent of phase — INELIGIBLE applications still proceed through blocking workflow. CLOSED is an independent flag layered on top of whatever status the request had. An application whose program has no trailing requirements (PREAPPROVAL, APPROVAL, ACCEPTANCE, workflow) goes straight to COMPLETE on submit, eligible or not; the request auto-completes on submit only when that holds for *every* application. An application with trailing requirements but no PREAPPROVAL/APPROVAL requirements is auto-advanced at submit (eligible or not) into its first blocking stage or to REVIEW_COMPLETE, and when every application is then REVIEW_COMPLETE/COMPLETE the review completes automatically too. A non-blocking workflow stage is editable from its `nonBlockingEmergence` AppRequest phase (default WORKFLOW_NONBLOCKING) until its optional `nonBlockingSunset` phase or until its program is marked complete, whichever comes first; both are enforced only in `RequirementPromptService.mayUpdate` (edit-only - a sunset does not change evaluation, so a requirement left PENDING at sunset still blocks COMPLETE). In the request's WORKFLOW_NONBLOCKING phase an application is WORKFLOW_NONBLOCKING while a non-blocking requirement is PENDING, then READY_TO_COMPLETE (still editable) until a reviewer runs `completeApplication` ("Complete review" in the reviewer screen's "Complete program review" panel, which shows for every program: red until READY_TO_COMPLETE, then blue, green once COMPLETE), which makes it COMPLETE and locks its non-blocking prompts; `reopenApplication` ("Edit review") undoes that. READY_FOR_WORKFLOW is blocking-workflow only. An application with no non-blocking stage still open (none, or all past their sunset) goes straight to COMPLETE and can be neither marked nor reopened. `Application.completesAfterNonBlocking` tells the UI which kind it is: when false, the panel's "Complete review" performs the final `advanceWorkflow` (to REVIEW_COMPLETE) in place of the last section's "Mark complete", and "Edit review" is `reverseWorkflow`. `completeRequest` needs every application COMPLETE.
- **Authorization** — Roles map external groups to **Grants** of controls (grouped in Control Groups), optionally restricted by **Tags** (downstream developer-defined, derived from prompt answers, e.g. applicants that chose a specific college). **Exceptions** subtract tagged access from a role; exceptions never escape the role boundary - roles union.

## Conventions

- The `@txstate-mws` skills (graphql-server*, graphql-svelte*, mysql2-async) apply throughout — load the relevant one before working in api/ or ui/.
- Design decision: INELIGIBLE (dead) applications are NOT exempt from blocking workflow or status progression; skipping is modeled by requirements returning NOT_APPLICABLE.
